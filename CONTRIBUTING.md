# Contributing

## Окружение

```bash
python -m venv .venv
# Windows
.venv\Scripts\activate
# Linux/macOS
source .venv/bin/activate

pip install -e ".[dev]"
```

## Проверки перед коммитом

```bash
ruff check .        # линтер
mypy                # типы
pytest -q           # тесты
```

Это ровно те же три проверки, которые выполняет CI (GitHub Actions) на каждый push и
pull request, поэтому все три должны проходить локально.

Форматирование `ruff format` пока **не** обязательно и не проверяется в CI. Формат
кода задаётся линтером (`line-length = 100`, `target-version = py311` в
`pyproject.toml`); кода в репозитории он в целом соответствует.

Проверка типов настроена: `mypy` смотрит на папку `app` и требует аннотаций
везде. Настройки лежат в `[tool.mypy]` в `pyproject.toml`. Папка `tests` не
проверяется: тесты намеренно подсовывают хранилищам неправильные данные, и строгий
режим ругался бы на это ложно.

## Стандарты кода

- Python 3.11+, аннотации типов везде, `from __future__ import annotations`.
- Максимальная длина строки — 100 символов.
- Docstrings для модулей, классов и публичных функций, **на английском языке**: код
  публикуется на GitHub. Русскими могут быть тексты документации (`README.md`,
  `CHANGELOG.md`, этот файл).
- Файловый ввод-вывод — всегда с `encoding="utf-8"`.
- Логирование через `logging`, не `print`.
- Слои `core/`, `providers/`, `services/` не импортируют PySide6 — иначе ядро нельзя
  тестировать без графического окружения.
- Мёртвого кода быть не должно: неиспользуемый сигнал, функцию или `objectName`
  либо подключаем, либо удаляем.

## Сообщения коммитов

Conventional Commits, на английском языке:

```
feat: add model catalog caching
fix: correct price range calculation
docs: update contributing guide
chore: bump dependencies
```

Типы: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`.

Правила оформления:

- **Одна идея — один коммит, вместе со всей документацией об этой идее.** В коммит с
  кодом едут запись в `CHANGELOG.md` и удаление исправленного пункта из
  [docs/known-issues.md](docs/known-issues.md). Список известных проблем — это часть
  состояния проекта: коммит, который починил дефект, но оставил его в списке, делает
  список врущим.
- Отдельным `docs:` оставляют только то, что не связано с правкой кода: переписывание
  разделов документации, фиксация аудита. Критерий: если документ можно убрать из
  коммита и репозиторий останется связным — можно отделять; если документ описывает
  конкретное изменение — нельзя.
- Правки только в тексте, не связанные с кодом (опечатки, уточнение формулировок),
  копятся и едут одним коммитом, а не коммитом на каждый.
- В сообщении — то, что понятно пользователю: результат, а не внутренние этапы
  проекта и не названия приватных файлов.
- Коммит должен проходить `ruff check .`, `mypy` и `pytest -q` сам по себе.

## Известные дефекты

Перед началом работы посмотрите [docs/known-issues.md](docs/known-issues.md): там
описано, что уже сломано. Если вы это чините — удалите пункт из файла в том же коммите,
что и исправление, а не оставляйте его «исправленным»: список должен показывать
актуальное состояние.

## Сообщение о проблемах

Опишите шаги воспроизведения, ожидаемое и фактическое поведение. Не прикладывайте
API-ключи и персональные данные.

Если в сообщении может оказаться ключ — сначала отзовите его у агрегатора.
